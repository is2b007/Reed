# Remote MCP from Claude Android

Reed's **Remote Agent Access** mode lets Claude on the same Android tablet edit the active local Reed project without Git. It is optional, disabled by default, and expires after eight hours. Local authoring, storage, backup, validation, export, CLI, and desktop stdio MCP remain fully offline.

## Why a relay is required

Claude's Android app does not open a socket to another Android application. Claude custom connectors call a public remote MCP URL from Anthropic's cloud. Reed therefore uses a small relay that joins that public Streamable HTTP request to an outbound HTTPS long poll owned by the tablet:

```text
Claude Android
      │
      ▼
Anthropic connector infrastructure
      │  Streamable HTTP MCP over HTTPS
      ▼
Reed relay (transient memory only)
      │  authenticated HTTPS long poll
      ▼
Reed Android foreground service
      │
      ▼
Android ReedCore → local SQLite/WAL
```

The relay has no Reed account or project database. It keeps active channel hashes, queued requests, and pending responses in memory only. Restarting it loses active channels; a running tablet reconnects and registers again. Run one relay replica unless a future implementation adds a shared, ephemeral channel coordinator.

## Relay URL versus connector URL

These are two different values:

- **Relay service URL** is the public HTTPS origin of the deployed Reed relay, for example `https://relay.example.com`. A self-hosted/development build asks for this value in Reed.
- **Claude connector URL** is generated by Reed after Agent Access starts. It includes a random project channel and connector capability, for example `https://relay.example.com/mcp/<channel>?access_token=<capability>`. Paste this complete generated value into Claude. Treat it like a password.

This checkout includes the trusted Reed relay origin in `apps/android/gradle.properties`, so the Agent workspace does not ask for an undefined service URL. The origin is public configuration, not a credential, and no connection starts merely because it is compiled into the app. A self-hosted or CI build can override it with either the Gradle property or environment variable:

```sh
cd apps/android
./gradlew -PreedAgentRelayUrl=https://relay.example.com assembleRelease

# Equivalent for CI:
REED_AGENT_RELAY_URL=https://relay.example.com ./gradlew assembleRelease
```

The origin is not a credential. The project-scoped connector and device capabilities are generated on the tablet and are not compiled into the APK. Agent Access remains off until the person explicitly starts a session.

## Deploy the relay

The relay needs Node 22+ and a public HTTPS origin that can receive requests from Anthropic. It must not sit behind a VPN or private-only firewall.

Build the supplied container from the repository root. On Apple silicon, use Docker Buildx so the build stage runs natively while the final image targets Linux/AMD64:

```sh
docker buildx build --platform linux/amd64 --load \
  -f apps/relay/Dockerfile -t reed-relay .
docker run --read-only --tmpfs /tmp --cap-drop ALL -p 8787:8787 reed-relay
```

Terminate TLS at the hosting platform or a reverse proxy and forward it to port `8787`. Verify:

```sh
curl https://your-relay.example/healthz
```

Expected response:

```json
{"ok":true,"service":"reed-relay"}
```

### AWS Lightsail: Reed's supported hosted setup

For a small private deployment, use an Amazon Lightsail container service in Sydney (`ap-southeast-2`) with **Nano power and scale 1**. Lightsail supplies the public HTTPS origin, while the single replica preserves the relay's in-memory channel routing. As of July 20, 2026, the AWS API reports this capacity at **US$7/month** while enabled. This service is optional infrastructure: Reed authoring and local MCP remain offline, and Android does not contact it until a person starts Remote Agent Access.

Install and authenticate the AWS CLI and the Lightsail container plugin, then run the read-only preflight from the repository root:

```sh
aws login
pnpm relay:deploy:aws
```

Review the account, region, service, and capacity it prints. Deploy only after that is correct:

```sh
pnpm relay:deploy:aws -- --apply
```

The script builds the supplied container for Linux/AMD64, creates or reuses `reed-relay`, refuses an existing service whose scale is not exactly one, uploads the image, deploys port `8787`, waits for the health check, and prints the HTTPS relay origin. It never creates a database, volume, cache, queue, logging sink, or secret. AWS still charges while the Lightsail service is enabled; disable or delete it when it is no longer wanted.

Use a different account, region, or service name only through explicit environment values:

```sh
AWS_REGION=ap-southeast-2 REED_RELAY_SERVICE=reed-relay \
  pnpm relay:deploy:aws -- --apply
```

The current in-memory design intentionally does not use ECS autoscaling, a multi-replica load balancer, Lambda, or App Runner. AWS stopped accepting new App Runner customers on March 31, 2026; even where an older account can still use it, automatic instance behavior is a poor match for this one-process relay.

Production requirements:

- HTTPS with a publicly trusted certificate;
- one active replica;
- request bodies and authorization headers excluded from logs;
- query strings redacted from proxy/access logs because the connector capability is carried in the MCP URL;
- request-body limit of at least 1 MiB and an upstream timeout above 45 seconds;
- no response caching;
- no persistence, analytics, tracing payload capture, or request replay.

### Hosting note: Vercel is not the current relay target

Do not deploy the current in-memory relay as an ordinary Vercel Function or Vercel Service. Vercel creates request invocations, can route concurrent traffic to multiple instances, and scales idle instances to zero. Reed's current bridge requires the tablet long poll and Claude request to reach the same live process, with no database or durable queue containing project content. See Vercel's [Functions lifecycle](https://vercel.com/docs/functions) and [container comparison](https://vercel.com/kb/guide/docker-on-vercel-vs-render).

Use a single-instance, always-on container host with HTTPS and query-string redaction. Vercel would become suitable only after a different ephemeral coordinator is designed and audited without persisting MCP request or response bodies.

The relay itself enforces a 1 MiB body limit, constant-time capability comparison, a maximum of 16 queued calls per channel, a maximum 24-hour session, a 45-second MCP timeout, and no-store response headers.

Verify a deployed origin end to end with a temporary in-memory channel and the official MCP client. The verifier generates short-lived random capabilities, never prints them, and disconnects when it finishes:

```sh
pnpm relay:verify -- https://your-relay.example
```

## Connect Reed and Claude

1. Open the project in Reed Android.
2. Open **Agent** in the project command bar.
3. Confirm the preconfigured relay origin, or enter the origin of your self-hosted relay, such as `https://your-relay.example`.
4. Press **Start 8-hour session** and approve the notification permission and confirmation.
5. Keep the persistent **Claude access active** notification present.
6. Copy the generated custom connector URL. Treat the complete URL like a password.
7. In Claude, open **Customize → Connectors → Add custom connector**.
8. Name it **Reed**, paste the URL, and add it.
9. In a conversation, open the **+** menu, choose **Connectors**, and enable Reed.
10. Ask Claude to call `get_schema`, `list_projects`, `list_scenes`, and `get_validation_report` before editing.

The connector URL is stable for that local project, so it can be reused across later sessions with the same relay origin. It answers only while the tablet has explicitly enabled Agent Access. **Rotate connector secret** invalidates the saved capability and produces a different URL the next time access starts.

## Background behavior

- Switching from Reed to Claude keeps the foreground service and tunnel running.
- Removing Reed's activity from Recents does not stop the service.
- The notification's **Disconnect** action immediately revokes the active relay channel.
- Android **Active apps → Stop**, Force stop, process death under extreme pressure, or tablet restart ends access. Reed intentionally does not silently restart authorization.
- A network interruption changes the workspace and notification to **Reconnecting**. Calls fail instead of being persisted for later execution.
- Returning to Reed reloads the active graph. Split-screen changes also appear while both apps remain open.
- Expiry disconnects the relay and removes the foreground notification.

## MCP safety boundary

Remote tools can read project structure and create or edit scenes, conversations, characters, variables, text, nodes, links, conditions, sequences, tags, and layout through `com.reed.core.ReedCore`.

`get_schema` also returns Reed's bundled game-language catalog and the IETF BCP 47 language-tag contract. `update_project` can change the active project's enabled languages and default writing language with `expectedVersion`; newly enabled languages receive blank text rows, while disabling a language preserves its existing text for later re-enabling. This is the same versioned operation used by Android's Project Settings workspace.

They cannot:

- execute Git, create commits, fetch, push, or open pull requests;
- read or write arbitrary files;
- execute shell commands;
- access raw SQLite or canonical JSON directly;
- promote agent text above `Polished`;
- modify or delete Final content;
- delete a node without repeating its exact permanent Line ID;
- bypass an `expectedVersion` conflict.

Every successful mutation is versioned and recorded with source `agent`. Editing recorded-or-later voice text returns its voice state to `Rework`.
